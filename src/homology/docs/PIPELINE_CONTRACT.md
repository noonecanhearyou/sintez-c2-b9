# Договор обмена: Homology → общий пайплайн

Версия формата: 1. Это реализованное предложение интерфейса; команда ещё должна подтвердить набор видов и научные пороги. Модуль не присваивает класс происхождения.

## Вход

- FASTA белков: уникальный `protein_id` в первом слове заголовка.
- TSV `protein_id<TAB>gene_id`, с точным заголовком. Общий ключ трёх блоков — `gene_id`.
- `query_species`: стабильный код вида (`dmel` и т. п.).
- Целевые базы: уникальный ID, код вида, точная версия сборки/аннотации, тип `protein` или `genome`, FASTA. Для собственного протеома обязательна таблица protein → gene; для остальных её также следует предоставлять.
- Конфигурация фильтров, пути к BLAST, число потоков, тайм-аут в секундах на процесс.

Источники, даты получения и версии находятся в `data/<source>/source.json`; выбор запросов и хэши протеома — в `data/<queries>/selection.json`. В `run.json` сохранены абсолютные пути команд, версии BLAST и хэши фактически использованных входов. Для переноса следует передавать исходники, конфигурации и результаты вместе с метаданными данных.

## Единицы и координаты

- Identity и покрытия — проценты, 0–100.
- `query_start/end` всегда относятся к аминокислотному запросу.
- В BLASTP `target_start/end` измеряются в аминокислотах; в TBLASTN — в нуклеотидах.
- `homology_hits.tsv`: нормализованные target start ≤ end, отсчёт от 1, обе границы включены. Направление хранится отдельно. Исходный порядок координат доступен в `raw`.
- `candidate_loci.tsv`: обе формы — `start_1based/end_1based` и `start_0based/end_0based_exclusive`, пригодные для BED.
- Идентификатор контига должен использоваться строго с указанной сборкой. Координаты из разных сборок или исходных коротких участков нельзя смешивать.
- `target_coverage` для TBLASTN — доля полного контига, не покрытие предполагаемого гена. Не используйте её для фильтрации полноты гена.

## Фильтрация

1. BLAST сохраняет HSP с E-value ≤ `search_evalue`.
2. Для собственного вида исключаются все белки с тем же gene ID, включая другие изоформы.
3. HSP проверяются по `accept_evalue` и `min_identity`.
4. BLASTP: объединяются интервалы запроса подходящих HSP к одному целевому белку; перекрытия считаются один раз. TBLASTN: покрытие считается отдельно для каждого HSP, без автоматического объединения локусов/экзонов.
5. Применяется порог покрытия. Отфильтрованные HSP остаются в таблице с причиной.

`passes_filters` — `true`/`false`. Причины: `same_gene_or_isoform`, `evalue`, `identity`, `query_coverage`. Пустая причина означает принятую строку.

`quality`: `broad_coverage_candidate` (покрытие ≥80%), `partial_candidate` (прошёл фильтры, но покрытие <80%), `significant_partial_similarity` (значимое сходство, не прошедшее покрытие), `filtered`. Это описания результата, не вероятности происхождения и не калиброванная confidence.

## Сводка на ген

- `paralog_candidate_count`, `paralog_gene_ids`: уникальные гены своего вида, прошедшие фильтры.
- `protein_hit_species`, `genome_hit_species`: виды с принятыми совпадениями; списки разделены запятыми.
- `partial_similarity_gene_ids`: гены своего вида с частичным статистически значимым сходством; список может пересекаться с принятыми кандидатами, если разные HSP/изоформы дали разные результаты.
- `partial_protein_species`, `partial_genome_species`: виды с таким частичным сходством.
- `best_protein_*`, `best_genome_*`: принятое совпадение с наибольшим bitscore; лучшее белковое совпадение может быть из своего вида. Подробности и тип поиска доступны в `homology_hits.tsv`. Равные баллы сохраняют первое совпадение в порядке конфигурации/вывода BLAST.
- `completed_targets`, `error_targets`, `not_run_targets`: число целевых поисков, не число видов.
- `limitations`: ограничения; пустые списки сами по себе не доказывают отсутствие родства.

## Состояния и ошибки

`search_status.tsv` имеет строку на каждый query/target:

| status | Смысл |
|---|---|
| `completed_with_hits` | Есть принятые HSP |
| `completed_no_accepted_hits` | Поиск выполнен; принятых HSP нет, частичные совпадения возможны |
| `not_run` | Цель отключена в конфигурации |
| `error` | Ошибка построения базы, поиска, чтения или проверки результата |

`raw_hsp_count` — число сохранённых BLAST HSP до фильтрации интерпретации; это не все совпадения, которые существовали бы при другом поисковом пороге. Ошибочная цель имеет неизвестные результаты, даже если счётчики равны 0.

Общий `run.json.status`: `completed`, `partial_error`, `error`, `partial_not_run`, `cancelled`; во время работы — `running`. `completed` относится только к целям этой конфигурации. Два вида в конфигурации не означают проверку всех 28 видов кейса. Неперечисленные цели вообще не анализировались.

CLI возвращает 0 при completed/partial_not_run, 2 при error/partial_error/cancelled, 1 при неправильном вызове. Потребитель должен читать статус, а не только код завершения. При фатальной ошибке до создания output (например, несуществующий вход) run.json ещё не существует.

## Передача Synteny и ORF

`candidate_loci.tsv` содержит одну строку на принятый геномный HSP. Это области совпадений, не полные границы генов. Они не объединены и не расширены фланками. Участник Synteny проверяет соответствующее окружение и отличает локусы от дополнительных родственных копий. Участник ORF получает выбранный локус, область для извлечения и требования к цепи; проверяет структуру, рамку, стопы, возможные интроны и качество сборки.

Для дополнительной чувствительности участникам доступны также геномные строки `significant_partial_similarity` из `homology_hits.tsv`; в `candidate_loci.tsv` они намеренно не включены как принятые. Команда должна решить, какие из них направлять на ручную проверку.

## Использование классификатором

Сначала проверить общий статус и статусы нужных видов. Затем учитывать принятые и частичные совпадения вместе с Synteny/ORF. Запрещено правило «пустой список → de novo». Не следует автоматически называть межвидовое совпадение ортологом или совпадение в своём виде доказанной дупликацией исследуемого гена.

Координаты исходного гена dmel доступны в `data/<queries>/annotation.tsv`, колонка `location`. Это исходное выражение FlyBase (`join`, `complement` и т. п.), а не готовая BED-строка. Для его использования нужно учитывать структуру экзонов и сборку r6.36.

В пакетном режиме `raw/` и `db/` находятся внутри `targets/<id>/`; при выполнении по группам — внутри `all_species_stageN/targets/<id>/`. Общий `run.json` содержит ссылки и хэши дочерних манифестов. В завершённой общей сводке списки кандидатов и видов объединены без повторного подсчёта, а состояния сохранены для всех пар query/target (41 340 в итоговом наборе без Aedes aegypti).

Текущий завершённый набор — `results/without_aaeg/`: 27 видов, 53 базы. Aedes aegypti явно указан в excluded_species; его белковые и геномные результаты не участвуют в выводах. Пустой результат по этому виду не формируется.
